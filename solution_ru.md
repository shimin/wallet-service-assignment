# Решение

В ветке fix/solution. В истории коммитов старался разделять упавший тест и за ним фикс, тесты лежат в internal/storage и internal/money:

```bash
docker compose up -d postgres nats
go test ./... -count=1
```

## Ход решения

1. Жалоба QA на несовпадающие балансы после нагрузочного тестирования намекает на некие гонки с полем балансов.

   1\.1\. Код HandleBalance сразу вызывает желание сначала исправить возврат корректного баланса, однако в процессе тянет проверить и еще исправить журнал транзакций из-за того, что валюта берется одним запросом, а баланс считается по сумме транзакций в таблице transactions (фиксим возврат баланса, запись в журнал - в п.3)

2. Тикет о списании средств, при котором деньги ушли с одного счёта и так и не появились на другом - неатомарный перевод, два кейса:

   2\.1\. Перевод на несуществующий кошелек

   2\.2\. Ошибки коннекта или локи в БД

3. Глядя на остальные функи Deposit/Withdraw/Transfer заметил неатомарный апдейт баланса и записи транзакции

4. Вопрос от финансов "может ли повторно отправленный запрос примениться дважды" намекает на проблемы с дедупликацией запросов

5. Встречные переводы A -> B и B -> A запущенные одновременно создают дедлок. Заметил не сразу, только когда тест начал гонять переводы в обе стороны

6. Суммы не проверялись вообще: депозит с отрицательной суммой уходил в balance + (-100), то есть в списание мимо проверки достаточности средств, баланс уходил в минус. А 1e500 роняло json.Unmarshal, после чего сообщение просто дропалось - ни completed, ни failed, отправитель ждал таймаута

## Фиксы

1. В HandleBalance возвращать поле wallets.balance а не сумму из журнала транзакций

2. Устранить гонки при обновлении балансов - избежать ошибок в будущем:

   2\.1\. Тесты гонок показывают проблемы с полем wallets.balance

   ```bash
   docker compose up -d postgres
   go test ./internal/storage/ -count=10 -timeout 300s
   ```

   2\.2\. Вариант с повышением уровня изоляции транз отброшен как дорогой по времени, реализации ретраев, и вообще неудобный

   2\.3\. В Withdraw и Transfer неатомарные обновления балансов - исправлена проверка баланса одним запросом в функции debit:

   ```sql
   UPDATE wallets SET balance = balance - $1, updated_at = NOW()
   WHERE wallet_id = $2 AND balance >= $1
   ```

   2\.4\. Дедлок на встречных переводах лечится детерминированным порядком блокировок: lockWallets берет оба кошелька одним SELECT ... ORDER BY wallet_id FOR UPDATE, дальше порядок списания-зачисления уже не важен

3. Починить запись в журнал transactions сделав их в одной транзакции с Deposit/Withdraw/Transfer

4. Завести таблицу requests с проверкой ON CONFLICT (request_id) DO NOTHING:
Альтернатива - поле idempotency_key в той же таблице, чтобы не смешивать сущности выбрана новая таблица

   4\.1\. Не трогаем старые записи, накатываем миграцию, создание новой таблицы не блочит прод, избавляемся от дублей в дальнейшей работе

   4\.2\. claimRequest перед Deposit/Withdraw/Transfer блочит/пропускает дублирующие запросы

   4\.3\. Добавил payload_fingerprint для более строгой защиты от одинаковых request_id с разным payload

5. Предложить способ аудита службе финансов для ручного устранения уже накопленных расхождений:

   5\.1\. Нет строки в transactions: если было движение средств, то истина у баланса, в transactions идёт корректирующая запись

   5\.2\. Баланс потерял апдейт: истина в transactions, баланс пересчитывается из транз со сверкой

   5\.3\. Запрос применен дважды: поиск дубликатов в transactions, лечится корректирующей записью

   5\.4\. Половина перевода: два кошелька разошлись на одну и ту же сумму - ручной разбор пары

   Возникает желание написать дополнительный сервис аудита-реконсиляции (вынесем за рамки решения):

   - вьюха entries для разбиения перевода на 2 транзы
   - вьюха wallet_reconciliation: полный список проблемных кошельков со знаком расхождения
   - поиск дубликатов GROUP BY request_id HAVING count(*) > 1
   - корректировки новой записью отдельной операции adjustment в transactions
   - таблица снимков reconciliation_runs (run_at, wallet_id, balance, ledger, diff)

Истории изменений баланса нет, неуспешные операции не записывались вовсе (нет status='failed'), события в NATS не персистятся. Значит для старых расхождений мы можем только сопоставить итоги, а не воспроизвести последовательность. Для 5.1. восстановить `request_id` и контрагента недостающей записи невозможно — только корректирующая проводка с пометкой «расхождение, обнаружено сверкой такой-то».

### Далее "менее критичные" проблемы, которые ранее при работе сервиса видимо, не стреляли, но оттого не менее критичные для будущей работы:

6. Ошибки округления при работе с float64 решены новым пакетом money (хочется лучше название), литерал из JSON -> money.Amount -> Value() -> текст -> NUMERIC(18,4) и обратно — текст -> Scan -> Amount

   6\.1\. Проверка суммы (положительная, представимая в scale 4 без округления, не больше 99999999999999.9999) живет в сторе - там же, где двигаются деньги, чтобы гарантия не зависела от вызывающего

   6\.2\. В хендлерах слой parse: разбирает payload, зовет validate() и на отказе публикует failed вместо тихого дропа. request_id для такого события достается отдельным разбором конверта - типизированный разбор на кривой сумме падает целиком, а порядок полей в JSON задает клиент

   6\.3\. Отпечаток идемпотентности считается от канонического StringFixed(4), а не от FormatFloat: раньше он округлял вместе с базой, и два разных запроса с одним request_id проходили как честный повтор

7. Не блокировались кроссвалютные переводы, добавлена валидация, проброс валюты и requireSameCurrency внутри транзакций

   7\.1\. requireSameCurrency сравнивает валюты двух кошельков под уже взятыми блокировками, requireCurrency сверяет валюту из запроса с валютой кошелька

   7\.2\. В Deposit кошелька может еще не быть, поэтому проверка вшита в сам upsert (WHERE $3 = '' OR wallets.currency = $3), affected == 0 означает несовпадение

   7\.3\. В хендлере проверяется формат кода: ^[A-Z]{3}$ или пусто

   7\.4\. Валюта добавлена в payload_fingerprint - иначе повтор с тем же request_id и другой валютой читается как честный ретрай

8. Конфиг молча подставлял дефолты: при пустых NATS_URL и PG_URL сервис шел на localhost с дев-кредами, зашитыми в код. На проде потерянная переменная окружения не роняла сервис, а уводила его не туда. Теперь Load() возвращает ошибку, main выходит с ней на старте, а креды из docker-compose переехали в тестовую фикстуру - go test по-прежнему запускается без переменных окружения, а локальный запуск сервиса требует их задать:

   ```bash
   set -a; source .env; set +a
   go run ./cmd/wallet-service
   ```

## Изменения контракта

Схема сообщений не менялась: amount остается JSON-числом, balance в ответе wallet.balance - тоже (печатается как 150.0000). Но поведение на границе изменилось, перед выкатом это стоит сверить с отправителями:

- сумма меньше 0.0001 теперь реджектится, а не округляется молча. Клиент, который сегодня шлет мелочь и получает округление вверх начнет получать отказ. Тихое округление денег хуже явного отказа, если есть логи, из любопытства стоит глянуть, есть ли такие отправители
- amount также принимается десятичной строкой - для клиентов, у которых своя сериализация использует float
- Withdraw с явной валютой из несуществующего кошелька возвращает "нет кошелька", раньше было "недостаточно средств"

## Допущения

- В проде работает один инстанс, допускаем что не требуется менять обычную подписку NATS nc.Conn.Subscribe на групповую QueueSubscribe с общей queue group (добавим в будущем, если решим масштабировать сервис)

- В HandleBalance в качестве результата возвращается сумма по записям транзакций кошелька, вместо поля wallets.balance - выглядит как какой-то недоделанный план на будущее, быстрейший фикс и срочный - возвращать значение поля баланса, поскольку проверка возможности совершить перевод выполняется именно по нему

  ```go
  SELECT balance FROM wallets...
  if balance < amount {
      return fmt.Errorf("insufficient funds")
  }
  ```

- хоть семантически правильнее восстанавливать баланс из транзакций, исходя из текущей ситуации, wallets.balance считаю за основу, поскольку списания-зачисления первой операцией применяются именно к этому полю, запись тразы могла падать - аудит расхождений в журнале транзакций будем вести относительно поля балансов

- при пустом currency считаю, что клиент подразумевает валюту кошелька. Иначе все нынешние отправители которые поле не шлют получат отказ. Кроссвалютный перевод при этом запрещен - кошельки сравниваются между собой

- кошелек, созданный первым депозитом, берет валюту из запроса, если не указана - USD

- В поле статуса пишется только 'completed' - полагаю, что всегда так и было, надо проверить на проде SELECT status, count(*) FROM transactions GROUP BY status;

## Что не сделано

- Колонка status фактически бесполезна - всегда 'completed' и ничего пока не отражает, неуспешные операции в базу не попадают, только публикуются в шину. После перевода операций в одну транзу отказ не оставляет лога и в requests: claimRequest откатывается вместе с операцией. Записывать попытку надо отдельной транзакцией после отката - вызывает сомнение, нужно ли вести журнал попыток, поэтому отложил
